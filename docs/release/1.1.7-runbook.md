# Release 1.1.7 — runbook

Covers `b821dc70..HEAD` plus the working tree. Android 1.1.6 (versionCode 12) is
live on Play; iOS is still on 1.1.5. 1.1.7 ships both together.

## What kind of release this is

**A pure-JS delta over the binary that shipped as 1.1.6.** Verified:

- no `package.json` changed anywhere in the range;
- `pnpm-lock.yaml` churn is quoting-only — 1452 packages before and after, **zero**
  resolved version changes;
- nothing changed in `mobile/plugins/`, `mobile/ios/`, `mobile/android/`, or
  `app.config.js`; the `app.json` diff is Prettier reflow plus the version bump.

So the native dependency graph is identical to what is already in the stores.
The rebuild is required only because `runtimeVersion.policy = "appVersion"` — a
1.1.7 bucket cannot be reached over the air from 1.1.6.

**If you want today's push fixes on existing Android 1.1.6 users now:** revert
`app.json` to `1.1.6`, `eas update --branch production`, then set 1.1.7 and build.
Otherwise just build.

### App Store introductory offers are not at risk

Offers live on the *subscription product*, not the app version — shipping a
binary does not touch them. What removed them previously is a different
mechanism: an offer still **pending review** is bundled into the version
submission, and cancelling that submission reverts the pending change. Approved
offers are unaffected.

Before submitting: confirm each offer reads **Approved / Active**, not "Waiting
for Review". If one is still pending, either let it approve first or simply do
not cancel the 1.1.7 submission while it is.

## Step 0 — commit (required)

`mobile/app/push-prompt.tsx` and `mobile/src/bootstrap/pushPromptState.ts` are
**untracked**. EAS Build archives git-tracked state, so a build from a
partially-committed tree ships `_layout.tsx` registering a `push-prompt` route
and `index.tsx` redirecting to it, with no file behind it — every authed user
whose OS permission is `undetermined` lands on expo-router's "Unmatched Route".

Same hazard on the backend: committing `notifications/models.py` without
`0003_pushticket.py` deploys code that queries a table that does not exist.

```bash
git add -A
git status --porcelain    # must be empty before building or deploying
```

## Step 1 — pre-flight the beat schedule

Run *before* deploying, while the old schedule is live:

```sql
SELECT name, task, enabled FROM django_celery_beat_periodictask
 WHERE task = 'education.tasks.emit_streak_about_to_expire';
```

Must return **exactly one** row named `emit-streak-about-to-expire`. The static
`beat_schedule` key matches that name, so `DatabaseScheduler` rewrites the row in
place at beat start — do **not** hand-create the new rows, that produces a second
row under a different name and genuine double-firing. If prod has a legacy
duplicate (as it does for `reset-inactive-streaks`), disable it now.

## Step 2 — Railway env

| Var | Action |
|---|---|
| `NOTIFICATION_DAILY_CAP` | **Leave unset.** Default is 2, which is what you want. |
| `CIO_JOURNEY_EVENTS_ENABLED` | **Verify `true`**, or the hourly streak sweep is a 24×/day no-op. |
| `TIME_ZONE` / `CELERY_TIMEZONE` | Leave at `Europe/London` — changing it during this deploy would shift the streak-hour fallback. |

No new required variables.

## Step 3 — deploy, in order

1. **web** — entrypoint runs `migrate`, applying `authentication.0032`
   (AddField, `default=''` → metadata-only on PG 11+), `authentication.0033`
   (CreateIndex on `core_userprofile`) and `notifications.0003` (CreateModel).
   All small at current table sizes. Confirm `GET /user/settings/` returns the new
   top-level `push_notifications`.
2. **worker** — must register `poll_expo_push_receipts` and the `PushTicket`
   model *before* beat starts scheduling them, or the first ticks queue as
   `NotRegistered`.
3. **beat, last** — this is what rewrites the streak entry to hourly and creates
   the two new rows.

Verify after beat restarts:

```sql
SELECT p.name, p.enabled, c.minute, c.hour, c.timezone
  FROM django_celery_beat_periodictask p
  JOIN django_celery_beat_crontabschedule c ON p.crontab_id = c.id
 WHERE p.name IN ('emit-streak-about-to-expire','poll-expo-push-receipts','prune-push-tickets');
```

Expect `0 / *`, `*/20 / *`, `30 / 4`, all `Europe/London`. Within ~40 minutes,
`grep expo_receipts_polled` in the worker logs. A first
`expo_push_credentials_broken` line is the payoff of this release — it means the
sweep just found something that used to be invisible.

## Step 4 — build and submit mobile

The backend is backward-compatible with 1.1.5/1.1.6 on every touched endpoint,
so it can go first safely.

```bash
cd mobile
npx expo install --check      # optional: 4 Expo packages are one patch behind
```

## Known, not fixed

Nothing here blocks the release.

- **i18next plurals are inert.** `packages/core/src/i18n/index.ts` sets
  `compatibilityJSON: "v3"`, whose suffixes are `_plural` (2-form languages) and
  `_0/_1/_2` (Romanian). The locale files use the **v4** suffixes `_one`/`_other`
  — roughly 25 pairs — so neither ever resolves and i18next falls back to the
  base key, which holds the *singular*. `t("subscriptions.trialDays", {count: 7})`
  renders "7 day trial" in EN today, and "7 zi de probă" in RO. Verified directly
  against i18next 23.16.8, both settings. The parity test cannot catch this: it
  compares key *sets*, and both locales carry the same dead keys.
  Fixing it means dropping `compatibilityJSON: "v3"` **and** adding `_few` for
  Romanian (v4 asks for it at counts 2–19; without it RO falls back to the
  singular again). That is an app-wide resolver change whose stated reason was
  Hermes lacking `Intl.PluralRules` — true once, not on SDK 54 — so it wants its
  own device pass rather than a same-day edit before a build.
- **Prerender snapshots** for `/` and `/subscriptions` bake in whatever pricing
  was live at build time and persist until the next deploy. (Measured on the
  deployed catalog: the promo is now yearly-only, so the next build's snapshots
  are correct.)
- **`within_frequency_cap`** still constrains nothing in practice: its only path
  is `send_ai_nudge_task`, reachable only from the disabled `send_ai_nudges_batch`.
  The journeys it names fire through CIO and never touch it. Real coordination
  needs CIO-side message limits.
- **Locale bundle weight**: web ships mobile-only namespaces (`demoLesson.*`,
  `settings.push.*`, `onboarding.notifPrompt.*`). Worth splitting a `mobile.json`
  namespace if bundle size becomes a concern.
- **`MAX_FONT_SCALE = 1.25`** now applies to `Text` and `TextInput` on both
  platforms; iOS users upgrading from 1.1.5 with "Larger Text" will see text
  shrink. Deliberate from the Android audit, but worth a device check.
- **Android `default` channel importance** dropped MAX → DEFAULT. Android ignores
  importance changes to an existing channel, so 1.1.6 upgraders keep MAX while
  fresh installs get DEFAULT. Cosmetic.
- **iOS push delivery is still unmeasurable.** Customer.io reports "delivered: 1"
  on iOS pushes because counting delivery needs a Notification Service Extension
  in the app. Adding one is a native target plus entitlements — it would turn
  1.1.7 from a pure-JS delta into a native change, so it belongs in its own
  release, not this one.
