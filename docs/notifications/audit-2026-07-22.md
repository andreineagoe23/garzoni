# Notification & email system audit — 2026-07-22

Scope: every push and email path (mobile, web, backend, Customer.io), the number
of permission prompts during onboarding, and whether disabling / re-enabling
notifications actually works end to end.

Trigger: `neagoeandrei23@gmail.com` (Django user 269) had received **zero** push
notifications on iPhone since signup.

---

## 1. The workflow, as it actually runs

### 1.1 Delivery paths

There are **four** independent ways a notification reaches a user. They do not
share a gate, which is the root of most findings below.

| # | Path | Trigger | Delivery | Content lives in |
|---|------|---------|----------|------------------|
| 1 | Backend → Expo | Celery task calls `TransactionalMessages.send_push` | `exp.host/--/api/v2/push/send`, addressed by `UserProfile.expo_push_token` | Python (`push_data` dict) |
| 2 | Backend → CIO transactional push | fallback when path 1 has no token or errors | CIO App API, addressed by person id | CIO template (27, 28, 45) |
| 3 | CIO journey push | domain event (`streak_about_to_expire`, `coach_nudge`, …) | CIO device table, registered by the RN SDK | CIO template (29, 31, 35, 39, 47, 52, 56) |
| 4 | CIO journey email | same events, other side of the branch | CIO / Mailgun | CIO template |

Paths 1+2 use the **Expo token stored in Django**. Path 3 uses the **native APNs
token registered by the CIO React Native SDK**. They are different tokens in
different stores, and nothing keeps them consistent.

### 1.2 Channel selection

`notifications/policy.py::resolve_channels` picks push vs email server-side, and
every CIO journey repeats the same decision with a `conditional_branch` action
named "Has Mobile App?" testing `has_mobile_app eq "true"`.

`has_mobile_app` is a profile trait written by `build_identify_traits`. Before
this audit it meant "the Django row has a non-empty `expo_push_token`" — a
signal about path 1, used to gate path 3.

### 1.3 Preference model

`UserEmailPreference`: `reminders`, `streak_alerts`, `weekly_digest`,
`billing_alerts`, `marketing`, `push_notifications`, `reminder_frequency`.
`push_notifications` is the push master switch, enforced in
`policy.should_send_push`. On the CIO side there is a separate global
`unsubscribed` boolean, only writable by CIO or by the bounce-suppression task.

## 2. Why user 269 never got a push

Four independent faults stacked. Any one of them alone would have caused
partial silence; together they produced total silence.

1. **The push master switch never persisted.** The mobile Settings toggle
   `PATCH`ed `{"push_notifications": …}` at the top level of the request body.
   `UserSettingsView.patch` only read `request.data["email_preferences"]`, so the
   field was silently dropped. The `GET` likewise only returned it nested, while
   the client read it from the top level — so the toggle always rendered "on"
   and `usePushNotifications` always treated push as allowed. The switch was
   cosmetic in both directions.

2. **The Expo token went stale and CIO was never told.** Expo returned
   `DeviceNotRegistered`; `_clear_stale_expo_token` nulled the Django column. The
   next profile sync then wrote `has_mobile_app=false` but **dropped**
   `expo_push_token` from the payload, because `build_identify_traits` filtered
   out empty strings. Result on the CIO profile: `has_mobile_app: "false"` next
   to a live-looking `ExponentPushToken[...]` that no longer worked.

3. **`has_mobile_app: false` closed every push branch.** With the gate false,
   all 13 running journeys routed this profile down the email side — even though
   CIO had three healthy iOS devices registered for it (`push_enabled: true`,
   `last_status: sent`).

4. **The profile was `unsubscribed: true`**, from an unsubscribe click on
   2026-05-27, so the email side was suppressed too. Every campaign except
   Payment Failed has `send_to_unsubscribed: false`.

Net effect, confirmed from the CIO delivery log: **no delivery of any kind since
2026-06-05**. Before that, every `ai-nudge` push failed with
`EMPTY_NOTIFICATION_BODY` (see finding 3.3).

## 3. Findings

### 3.1 Push master switch was inert (critical) — FIXED
`UserSettingsView` dropped the top-level `push_notifications` on write and did
not return it on read; mobile read and wrote only the top level. Disabling did
nothing; enabling did nothing.

*Fix:* `views_profile.py` now folds a top-level `push_notifications` into the
nested payload and mirrors it back on `GET`/`PATCH`. Clients resolve the value
through the new `resolvePushEnabled()` helper in `@garzoni/core`, which reads the
nested key and falls back correctly.

### 3.2 `has_mobile_app` was the wrong signal, and went stale (critical) — FIXED
- Empty `expo_push_token` was filtered out of identify payloads, so clearing the
  token locally never cleared it in CIO.
- `sync_device()` wrote the token without `has_mobile_app`, so the branch gate
  could disagree with the token beside it.
- The trait ignored `push_notifications`, so a user who turned push off still
  went down the push branch.

*Fix:* `has_mobile_app = bool(token) and push_opt_in`; `expo_push_token` added to
`_ALWAYS_SEND_TRAITS` so an empty value is transmitted; `sync_device()` now
carries `has_mobile_app`; `_clear_stale_expo_token` enqueues a CIO resync.

Blast radius before the fix, measured across all 98 CIO profiles: **4 profiles**
had a registered device or token but `has_mobile_app: false` — ids 247, 269, 320,
203. Two of those are the founder's own accounts, which is why this looked like
"push has never worked".

### 3.3 All three transactional push templates had an empty body (critical) — FIXED
Templates 27 (`portfolio-update`), 28 (`ai-nudge`) and 45
(`streak_about_to_expire`) had content only in `body_json`; the CIO sender reads
the top-level `body`. Every send failed with
`{"status":-1,"detail":"EMPTY_NOTIFICATION_BODY"}`.

The 2026-06-15 pass fixed the seven *campaign* push templates and missed the
three *transactional* ones. Fixed now via the API; verify with a live send.

### 3.4 The one-shot OS dialog could be spent cold (high) — FIXED
`usePushNotifications` ran `registerForPushAndSubmitToken()` on every foreground,
which called `requestPermissionsAsync()`. For anyone who did not pass through
mobile onboarding — signed up on the web, then installed the app — the system
dialog fired at an arbitrary moment with no priming, and iOS never shows it
again.

*Fix:* the background path now passes `{ prompt: false }` and only refreshes
tokens for already-granted devices. Prompting is reserved for the priming screen
and the Settings toggle.

### 3.5 Web-first users were never asked at all (high) — FIXED
`/onboarding` redirects users with a completed questionnaire straight to the
tabs, so they never saw `PushPromptScreen`. Combined with 3.4 they had no
prompt path whatsoever.

*Fix:* new `/push-prompt` route reusing the same priming screen, gated in
`app/index.tsx` on "never asked" + OS status `undetermined`, tracked by
`pushPromptState.ts`.

### 3.6 Re-enabling after an OS denial gave no feedback (high) — FIXED
Once the OS has recorded a denial, `requestPermissionsAsync` resolves instantly
as denied. The toggle flipped itself back with no message — indistinguishable
from a broken switch.

*Fix:* the toggle now checks `getPushPermissionStatus()` and offers
`Linking.openSettings()` when the OS is blocking, or surfaces the registration
error otherwise.

### 3.7 Re-subscribing to email was impossible (high) — FIXED
Profile identify never carries `unsubscribed` (deliberately — a blanket write
would undo bounce suppression), so nothing could ever clear it. A user who
unsubscribed once could re-tick "Tips and announcements" in Settings and change
nothing in CIO.

*Fix:* `resubscribe_customer_in_cio` task plus a `pre_save`/`post_save` pair on
`UserEmailPreference` that fires only on a `marketing` false→true transition.

### 3.8 Android push delivery hints missing (medium) — FIXED
`send_expo_push` sent no `channelId`, `sound` or `priority`. On Android 8+ the
app creates a `default` channel that the payload never referenced.

### 3.9 An email unsubscribe silently killed push (partly fixed)
Push transactional messages 19 (`portfolio-update`) and 20 (`ai-nudge`) had
`send_to_unsubscribed: false`, so unsubscribing from *email* also stopped
*push* — not what a user asking to stop emails intends, and it costs a
retention channel from people who never objected to it.

*Applied:* 19 and 20 now have `send_to_unsubscribed: true` (21 already did).
Push is treated as its own channel, still gated by the in-app push toggle
(`push_notifications` → `has_mobile_app` / `should_send_push`), so a user who
turns push off in Settings is still respected.

*Still open:* 12 of 13 journeys keep `send_to_unsubscribed: false` at the
campaign level, so an unsubscribed profile is dropped before it reaches a
journey's push branch. Fixing that properly means modelling email and push as
separate subscription topics in CIO rather than flipping the campaign flag
(which would also un-suppress email). Dashboard work, not code.

### 3.10 The CIO unsubscribe webhook post-dates the incident (no action)
Webhook 2 subscribes to `customer_unsubscribed`, `email_unsubscribed`,
`customer_subscribed`, `email_bounced`, `email_spammed`, is enabled, and was
last active 2026-07-20. It was created 2026-05-30, three days *after* user 269
unsubscribed — which is why that unsubscribe was never mirrored into Django.
Not a live bug.

## 4. How many times we ask for permission

**Once**, and that is the right number.

Current flow for a mobile signup:

```
questionnaire → completion rewards → PlanReady → PushPromptScreen → paywall
                                                 └ custom priming screen
                                                   └ OS dialog only on "Turn on"
```

- Exactly one custom pre-permission screen (`PushPromptScreen`), which previews
  a realistic notification before spending the system dialog.
- Exactly one OS dialog, fired only when the user taps the positive CTA.
- Declining costs nothing and does not block onboarding.
- The Settings toggle is a user-initiated action, not a prompt.

This is the pattern Duolingo, Headspace and Calm use, and it is already
implemented correctly. The problems were never the count — they were that
**two other code paths could also raise the dialog or skip it entirely** (3.4,
3.5). With those fixed, the count is one ask per install, in a primed context.

### Built after the audit (same day)

- **Expo delivery receipts.** New `PushTicket` model + `poll_expo_push_receipts`
  every 20 min. A ticket only means "queued"; the receipt is the only place
  `InvalidCredentials` (revoked APNs key), `MismatchSenderId` (wrong FCM sender)
  or `DeviceNotRegistered` is ever reported. Sender-side codes log at ERROR with
  a pointer to `eas credentials`; `DeviceNotRegistered` clears the token and
  resyncs CIO. `prune_push_tickets` keeps 7 days.
- **Rolling local streak reminders.** `scheduleStreakReminder` now schedules a
  7-day window at 8pm local instead of one, with copy that escalates and then
  pivots from "save your streak" to "start a new one". Re-armed on each app
  open, so it keeps working for exactly the user who stopped opening the app.
  Files under the `streak` Android channel.
- **Android channels + per-topic control.** Five channels (`streak`, `lessons`,
  `billing`, `marketing`, `default`) so muting offers no longer mutes billing
  alerts. `should_send_push` now consults the matching per-topic preference, and
  the backend picks the channel via `push_channel_for_category`. The existing
  Settings switches were relabelled — they govern both channels, deliberately:
  a second parallel set of push switches would only invite the two to disagree.
- **Timezone-aware evening sweep.** `UserProfile.timezone_name` is reported by
  the device alongside the push token. `emit_streak_about_to_expire` now runs
  hourly and only picks users for whom it is 7pm locally. Previously a user in
  Los Angeles got their evening nudge at 11am.
- **Daily frequency cap.** `NOTIFICATION_DAILY_CAP` (default 2) caps
  non-operational messages per user per day, counted in cache. Several journeys
  could independently nudge the same lapsed user in one evening.

### Recommended next step (not implemented)

The one gap left versus Duolingo: they re-engage decliners with a *soft* in-app
prompt later, after value has landed, that deep-links to system settings rather
than re-requesting permission. Garzoni currently has no recovery path — a
decline during onboarding is permanent unless the user finds Settings.

Suggested: after the first completed lesson, if `getPushPermissionStatus()` is
`denied`, show a dismissible card ("Keep your streak alive — turn on reminders")
that calls `Linking.openSettings()`. Cap it at one showing, ever. Analytics for
this already exist (`push_prompt_shown` / `_accepted` / `_declined`).

Placement question worth an experiment: the prompt currently sits immediately
before the paywall. Moving it after the first lesson would ask at a higher-value
moment, and the `post_first_lesson` placement arm in `onboarding.tsx` is already
wired for that kind of split.

## 5. Verification checklist after deploy

1. Toggle push off in mobile Settings → `GET /user/settings/` returns
   `push_notifications: false` at the top level and nested; CIO profile shows
   `push_opt_in: false`, `has_mobile_app: false`, `expo_push_token: ""`.
2. Toggle back on → OS dialog (or the system-settings alert when blocked);
   CIO shows `has_mobile_app: true` and a fresh token.
3. Fire `send_ai_nudge_task` for a device user → Expo path succeeds; force the
   CIO fallback and confirm the delivery is `sent`, not `EMPTY_NOTIFICATION_BODY`.
4. Fresh install, sign in with a web-created account → `/push-prompt` appears
   once, never again.
5. Un-tick then re-tick "Tips and announcements" → CIO `unsubscribed` flips back
   to `false`.
